## 2. 背景

### 2.1 为什么要预创建（聚合的「发现」依赖）

当前单聊 `user_session` 行的**唯一创建者**是登录聚合（`distinct on` 从消息表发现会话 → upsert）。这带来两个问题：

1. 聚合发现查询（任务 09 V4）是跨 16 分区扫描 —— 想优化成 `user_session` 驱动的 LATERAL 点查，但**行不存在的会话永远发现不了**，优化被堵死；
2. 会话行存在依赖"登录聚合已跑过"，`/session/sync` 的前置（任务 05）也随之依赖。

群聊没有这个问题：入群那一刻就建行（任务 03 §6.3：`accept_group_invitation` → `init_for_group_join`）。本任务给单聊补上对称钩子 —— **好友接受时建行**。此后"关系成立"即行存在，聚合的发现职责降级为兜底。

> ✅ **后续修订（偏差记录 §1.7）**：发现兜底已随聚合迁出生产者**彻底删除** —— 单聊聚合改 `user_session` 驱动点查（`latest_by_session`），不再有 `distinct on` 全扫。本任务"关系成立即建行"从此是不变式，而非"兜底依赖"。

### 2.2 缺陷 R：`process_friend` 的事务是装饰性的

`friend_service.rs:138` `acquire_begin()` 拿到 `tx`，但事务块内的两条语句（`:150` `FriendRequestInfo::update_by_map`、`:163` `FriendLink::insert`）**传的都是 `rb`** —— 各自从连接池取连接执行，`tx.commit()` 提交的是一个空事务，rollback 对已执行语句无效。

后果：接受流程非原子（申请状态更新成功但好友关系插入失败的中间态）。本任务在同一段代码里新增多组写入，**必须真原子**，顺手把既有两条拉回事务。未上线无历史数据，行为变更无兼容成本。

## 3. 改造设计

### 3.1 前置消息：内容与方向（产品语义，实现前定死）

申请留言是**会话的前置消息** —— 会话的开篇由两条消息构成，构成一次自然对话：

```
A(申请人): [申请留言]        ← 存在请求行上: exit_request_info.request_message
                            例: "对不起，之前是我不对" / "我是老王，群里的"
B(接受人): [通过提示或留言]   ← 本次接受填写的 accept_message, 缺省用模板
                            模板: "我通过了你的好友申请，现在可以开始聊天了"
```

| 语义点 | 规则 |
|--------|------|
| 方向 | A 条 A→B；B 条 B→A —— 双方各有一条"自己发出的"消息，会话天然对称 |
| 未读归属 | A 条 → 未读落 B（B 虽在申请列表见过留言，但会话窗口因此自含开篇，可读可清）；B 条 → 未读落 A（A 得到"好友关系已成立"的明确信号） |
| 留空兜底 | `request_message` 空 → 默认文案常量；`accept_message` 空 → 通过模板。**每次接受恒写两条**，不按内容有无跳过 |
| 重加好友 | 每次成功接受都写**本次申请**的消息 —— 新申请 = 新留言（道歉场景：删好友 → 带道歉重新申请 → 通过 → 聊天窗口显示道歉，紧接在旧历史之后）。非刷屏：内容是真实留言，非重复模板 |
| 幂等源 | **请求状态迁移**（pending → accepted）每次恰好发生一次：接受后 `accept_status=1`，再处理同请求走 `get_request_info()` 找不到 pending 项 → "Request not found"。并发双击由事务 + `FriendLink` 主键冲突兜底（缺陷 R 修复后回滚真正生效）—— 不需要额外守卫条件 |
| `text_type` | 两条均 `0`（纯文本）—— 客户端零改动 |
| 时间戳 | 复用流程内 `now`（`get_now_time_stamp_as_millis()`），两条同刻，会话内排序按 id |

### 3.3 新增私有助手（`friend_service.rs` 文件内）

```rust
/// 申请留言缺省文案(申请时未填)。
const FRIEND_REQUEST_DEFAULT_MSG: &str = "我请求添加你为好友";
/// 通过提示缺省文案(通过时未填留言)。
const FRIEND_ACCEPT_DEFAULT_MSG: &str = "我通过了你的好友申请，现在可以开始聊天了";

/// 好友通过即建会话(任务04b)。
/// session + 双方 user_session + 两条前置消息(A 的申请留言 + B 的通过提示)。
/// 幂等源 = 调用方(请求状态迁移恰好一次), 本函数自身可重复执行无守卫。
async fn create_session_on_friend_accept(
    rb: &dyn Executor,
    request_user: &Uuid,                    // 申请人 A
    accept_user: &Uuid,                     // 接受人 B
    request_message: Option<&str>,          // 申请留言(可空)
    accept_message: Option<&str>,           // 通过留言(可空)
    now: i64,
) -> Result<(), anyhow::Error> {
    // rbdc::Uuid 与 uuid::Uuid 是不同类型, 沿用 add_user_chat_record 的边界转换惯例
    // (process_msg_service.rs:383-387, 任务01 §2 类型说明)
    let session_uuid = single_session_uuid(
        &uuid::Uuid::parse_str(&request_user.to_string())?,
        &uuid::Uuid::parse_str(&accept_user.to_string())?,
    );
    let su: Uuid = session_uuid.to_string().parse()?;

    // 1. session 行(幂等: 已存在则 DO NOTHING)
    Session::upsert(rb, &Session {
        session_uuid: su.clone(),
        session_type: Some(SESSION_TYPE_SINGLE),
        last_message_id: None, last_message_at: None, last_preview: None,
        created_at: None, updated_at: None,
    }).await?;

    // 2. 双方 user_session(幂等 upsert; 游标 NULL)
    //    ⚠️ 用裸 upsert, 不用 init_for_group_join —— 群聊入群游标推到 max(历史不算未读),
    //    单聊的前置消息本身就是"我们成为好友了"的通知, 必须保留未读。语义相反, 勿"顺手统一"。
    UserSession::upsert(rb, &UserSession {
        id: None, user_uuid: request_user.clone(), session_uuid: su.clone(),
        session_type: Some(SESSION_TYPE_SINGLE), peer_uuid: Some(accept_user.clone()),
        last_read_id: None, synced_id: None, pinned: None, muted: None,
        deleted_at: None, created_at: None, updated_at: None,
    }).await?;
    UserSession::upsert(rb, &UserSession {
        id: None, user_uuid: accept_user.clone(), session_uuid: su.clone(),
        session_type: Some(SESSION_TYPE_SINGLE), peer_uuid: Some(request_user.clone()),
        last_read_id: None, synced_id: None, pinned: None, muted: None,
        deleted_at: None, created_at: None, updated_at: None,
    }).await?;

    // 3. 两条前置消息(每次接受都写, 内容取本次申请)
    let msg_a = request_message
        .filter(|s| !s.is_empty())
        .unwrap_or(FRIEND_REQUEST_DEFAULT_MSG);
    let msg_b = accept_message
        .filter(|s| !s.is_empty())
        .unwrap_or(FRIEND_ACCEPT_DEFAULT_MSG);
    // 3.1 申请留言: A → B
    ChatMessageRecord::insert(rb, &ChatMessageRecord {
        id: None,
        session_uuid: su.clone(),
        nano_id: Some(nanoid::nanoid!()),
        timestamp: Some(now),
        raw: Bytes::from(msg_a.as_bytes().to_vec()),
        text_type: Some(0),
        send_user: request_user.clone(),
        recv_user: accept_user.clone(),
    }).await?;
    // 3.2 通过提示: B → A(后写, id 更大 —— 会话排序即"对话顺序")
    ChatMessageRecord::insert(rb, &ChatMessageRecord {
        id: None,
        session_uuid: su.clone(),
        nano_id: Some(nanoid::nanoid!()),
        timestamp: Some(now),
        raw: Bytes::from(msg_b.as_bytes().to_vec()),
        text_type: Some(0),
        send_user: accept_user.clone(),
        recv_user: request_user.clone(),
    }).await?;

    // 4. 会话摘要指向 B 的消息(最新一条)。insert 不回填 bigserial id,
    //    取会话最大 id(单分区索引 top-1, 任务04 既有方法) —— 即 B 条的 id
    let max_id = ChatMessageRecord::max_id_by_session(rb, &su).await?;
    Session::update_last_message(rb, &su, max_id, now, Some(msg_b)).await?;
    Ok(())
}
```

> preview 规则与任务 06 §2 一致（内容即文案，长度远小于 256 截断线）—— 列表**立即**有摘要，不等聚合。

依赖引入：`http_service/Cargo.toml` 加 `nanoid = { workspace = true }`（workspace 根已定义 `nanoid = "0.4.0"`，`common` / `quic_service` 同款引用）。

### 3.4 场景语义记录

| # | 场景 | 行为 |
|---|------|------|
| 1 | 首次成为好友 | 会话以两条消息开篇（A 留言 + B 通过）；A 未读 1（B 条），B 未读 1（A 条）；双方列表均出现且置前 |
| 2 | A 离线时被通过 | 登录聚合 no-op（行已存在）；`/session/sync`（或临时 `/msg/get_unread_chat_record`）从 `synced_id=0` 起点拉到前置消息 —— **不依赖聚合发现**，本任务的核心收益 |
| 3 | A 在线时被通过 | 无 QUIC 推送 → A 在下次列表刷新/同步时见到（会话凭空出现在列表顶部）。可接受：A 正在等申请结果，大概率开着申请列表页 |
| 4 | 删好友后重加 | `friend_link.is_del=true` 允许再申请再通过（`:119-122` 只挡 `is_del=false`）；新请求 → 新留言 → **聊天窗口显示本次的道歉/说明**，紧接旧历史之后。旧会话复活带全部历史 |
| 5 | 双端并发通过同一申请 | `FriendLink` 主键冲突 → 事务整体回滚（缺陷 R 修复后真正生效）→ 无半成品会话行/消息 |
| 6 | 同一请求重复接受 | `accept_status=1` 后不再命中 pending → "Request not found"，不产生重复消息 |

## 12. 实施记录（实施后补记）

任务 04b 已实施完成。与任务书原文的差异、发现的缺陷与验证结果如下。

### 12.1 与任务书原文的差异

1. **`user_session` 游标落库为 0 而非 NULL**：`UserSession::upsert` 用 `COALESCE($5,0)` / `COALESCE($6,0)`（`user_session.rs:47`），故 §3.3 注释与 §4 第一条断言中的「游标 NULL」实为 `Some(0)`；测试按 `Some(0)` 断言。
2. **`rbdc::Uuid` 是新类型而非 re-export**：`rbdc::Uuid` 为 `struct Uuid(pub String)`（`rbdc/src/types/uuid.rs:9`），助手参数用 `RbdcUuid`，派生走 `to_string()` / `parse()` 边界转换（§3.3 原文注释「不同类型」判断正确，此处仅补实现细节）。
3. **文案常量可见性**：`FRIEND_REQUEST_DEFAULT_MSG` / `FRIEND_ACCEPT_DEFAULT_MSG` 由 §3.3 的私有改为 `pub const`，供集成测试复用（仍各一处定义）。
4. **原子性用例失败注入具体化**：§4 的「mock `FriendLink::insert` 冲突」落地为——预插一条与待处理请求**同 uuid、不同用户对**的 `friend_link`，令接受分支的 `FriendLink::insert` 撞主键。
5. **测试驱动方式**：§4 追加进 `http_service_integration_test.rs` 的 §8（`catch_unwind` 内），**直接调 service 函数**（`add_friend` / `process_friend` / `get_unread_chat_record` / `delete_friend_service`），新建 6 个临时用户，不引入二次登录。

### 12.2 缺陷 S（本任务发现并修复）：重加好友撞 `friend_link_unique`

任务书 §3.4-4 假设「删好友后重加」可用，但 `delete_friend_service` 是**软删**（`is_del=true`，行仍在），而 `friend_link` 有 `UNIQUE (request_user, accept_user)`（`friend_link.sql:15`）；原 `process_friend` 无条件 `FriendLink::insert` → 重加时唯一约束冲突、接受流程报错（§8 重加用例直接暴露）。

### 12.3 §1.2 / §3.4-3「好友通过无 QUIC 推送」表述订正
