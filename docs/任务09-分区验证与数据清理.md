### 2.4 V4 超标的既定升级路径：聚合 LATERAL 重写（前提 = 任务 04b）

任务 04b（好友通过即建会话）落地后，单聊 `user_session` 行在**关系成立时**已存在 —— 聚合的「会话发现」职责降级为兜底，单聊聚合可从消息表扫描改为 `user_session` 驱动（与群聊路径 `aggregate.rs:88-118` 对称）：

```sql
-- 替换 ChatMessageRecord::latest_per_session_for_user(chat_message_record.rs:76)
SELECT us.session_uuid, m.id, m.timestamp, m.send_user, m.recv_user
FROM user_session us
LEFT JOIN LATERAL (
    SELECT * FROM chat_message_record m
    WHERE m.session_uuid = us.session_uuid   -- 每次迭代运行时剪枝到单个分区
    ORDER BY m.id DESC LIMIT 1               -- idx_chat_msg_pull 反向索引取首行
) m ON true
WHERE us.user_uuid = $1
```

- 成本从「16 分区扫我的全部历史消息行」降为 **O(会话数 × log n)**；`send_user` 分支每分区 seq scan 的问题一并消失
- 会话多时仍会碰全 16 分区（hash 分散）—— 赢的是**分区内行选择性**，不是分区数
- **触发条件**：仅当 V4 实测秒级才切换；切换后登录时的 `distinct on` 保留一轮作为发现兜底（防好友钩子未覆盖的边角，如未来 session_type 3/4 无好友关系的系统会话）
- 群聊侧无需改动（已是 membership 驱动逐群点查）

## 3. 数据清理任务（7 天窗口）

### 3.1 语义安全性论证（先回答"删了会不会坏"）

| 依赖方 | 影响 | 结论 |
|--------|------|------|
| `/session/sync` 游标 | 删的是 `timestamp < boundary`（窗口外）—— 同步查询本身带同款窗口过滤，**查询结果不变**；`truncated_by_window` 语义不变（探测的是"游标之后窗口之外"，删除后探测为 false —— **语义漂移**：删过之后"被截断"无从告知。**接受**：清理是运维动作，产品语义以"超出 7 天"为准，删除让截断提示从"有消息被跳过"变为"无消息"—— 提示消失在数天后属自然衰减，非 bug） |
| 未读数（`id > last_read_id` 计数） | 删的是旧消息（`id < boundary` 时代），未读恒为新消息 → **不变** |
| `session.last_message_*` | 若会话最后一条恰被删（用户 7 天无动静）：`last_message_id` 指向已删行，但列表展示用的是 `last_preview`/`last_message_at`（存在 session 行上）→ **展示不变**；下次该会话来新消息，单调更新自然覆盖 |
| FK | 两张消息表无被引用关系 → 删除无 FK 阻碍 |

### 3.2 entity 层清理方法

`session_entity/aggregate.rs` 或新 `entity/src/models/session_entity/cleanup.rs`：

```rust
/// 分批删除窗口外消息, 返回本批删除行数(0 = 本轮清完)。
/// ⚠️ 定位必须用 id —— ctid 是分区内局部值, 跨分区会误删(主方案 §15.6 陷阱)。
pub async fn delete_messages_before(
    rb: &dyn Executor,
    boundary: i64,
    batch: u32,
) -> Result<(u64, u64), rbatis::Error> {
    // 单聊一批 + 群聊一批, 返回 (single_deleted, group_deleted)
    let s = rb.exec(
        "DELETE FROM chat_message_record WHERE id IN (
             SELECT id FROM chat_message_record WHERE \"timestamp\" < $1 LIMIT $2)",
        vec![value!(boundary), value!(batch)],
    ).await?;
    let g = rb.exec(
        "DELETE FROM group_message_record WHERE id IN (
             SELECT id FROM group_message_record WHERE \"timestamp\" < $1 LIMIT $2)",
        vec![value!(boundary), value!(batch)],
    ).await?;
    Ok((s.rows_affected, g.rows_affected))
}
```

> 群消息同样 7 天清理：与单聊窗口对齐。群漫游（`/group/chat/message/history` offset 翻历史）超过 7 天的部分回退到客户端本地 SQLite —— 与单聊行为一致，产品语义统一。

### 3.3 调度（应用内，api 启动时 spawn）

`crates/api/src/init_server.rs`（`start_server` 内、`HttpServer` 启动前）：

```rust
// 每日数据清理: 启动即跑一轮, 之后每 24h 循环。
// 分批 10000, 循环至清空; 单批失败仅打日志, 下一轮重试(幂等)。
{
    let state = state.clone();
    tokio::spawn(async move {
        let mut tick = tokio::time::interval(Duration::from_secs(24 * 3600));
        tick.set_missed_tick_behavior(tokio::time::MissedTickBehavior::Delay);
        loop {
            tick.tick().await;
            let boundary = chrono::Utc::now().timestamp_millis()
                - SYNC_WINDOW_DAYS * 24 * 3600 * 1000;
            let mut total = 0u64;
            loop {
                match cleanup::delete_messages_before(state.db(), boundary, 10_000).await {
                    Ok((s, g)) if s + g > 0 => total += s + g,
                    Ok(_) => break,
                    Err(e) => { error!("[cleanup] 清理批次失败: {e}"); break; }
                }
            }
            info!("[cleanup] 窗口外消息清理完成: {total} 行, boundary={boundary}");
        }
    });
}
```

> `interval` 首次 tick 立即触发 —— 启动即跑一轮 ✓。常量 `SYNC_WINDOW_DAYS` 与 `/session/sync` 的窗口共用一处定义（避免双源漂移：把任务 05 的模块内 const 提升到 `common::config_str`，两处引用）。

## 4. 定时兜底聚合（30 秒周期）

### 4.1 要解决的场景

上线/下线触发（任务 03）覆盖不了**持续在线**用户：一直在线持续收消息 → `session.last_message_*` 停留在上线时刻 → 会话列表排序陈旧。兜底 = 周期性对本机在线用户重聚合。

### 4.2 实现（quic_service，集群友好）

`quic_service/src/external/` 新增 spawn（与现有保活/续期任务同模式，参考 `quic_server.rs` 的节点注册续期任务先例）：

```rust
/// 兜底聚合: 每 30s 对本机在线用户跑一次 aggregate(幂等)。
/// 每节点只处理自己 DashMap 上的连接 —— 集群天然分担, 不跨节点。
async fn start_periodic_aggregate(
    core: CoreState,
    connections: Arc<DashMap<String, QuicConnection>>,
) {
    let mut tick = tokio::time::interval(Duration::from_secs(30));
    loop {
        tick.tick().await;
        // 从连接键提取去重 uuid(PC/MOBILE 平台键格式: "PLATFORM:...:UUID:TEXT")
        let users = extract_distinct_uuids(&connections);
        for u in users {
            if let Err(e) = aggregate_user_sessions(&core.db, &u).await {
                warn!("[session] 兜底聚合失败: user={u} err={e:?}");
            }
        }
    }
}
```

> **性能注记（连回 §2）**：每个在线用户每 30 秒一次全量聚合 = V4 查询 × 在线人数 / 30s。若 V4 实测为百毫秒级且在线用户上百，本任务的频率需要下调（60s/120s）或引入 §1.2 的脏会话标记 —— **用 V4 的实测数据定频率**，文档默认 30s 仅是起点。
