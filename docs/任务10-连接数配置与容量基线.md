## 2. 背景：为什么现在该放开 1000

### 2.1 现状

`crates/quic_service/src/external/config.rs:31` 硬编码 `max_connections: 1000`，调用链：

```
init_server.rs:38   ChatNodeConfig::from_toml_str(&resolved_content)
      │
quic_server.rs:332  → user_online(..., config.max_connections)
      │
quic_server.rs:671  if connections.len() >= max_connections && !has_old_connection {
                        return Err(anyhow!("Maximum connections reached: ..."));
                    }
```

### 2.2 放开是零代价的

三点事实决定了这个上限**只是策略值，不是资源值**：

1. **不做内存预分配** —— `max_connections` 仅用于与 `connections.len()`（DashMap 实时大小）比较，DashMap 按需增长。改大不增加任何静态内存占用。
2. **老连接重连永不被拒** —— 条件带 `&& !has_old_connection`：同一用户同一平台的**重连**（`connections.contains_key(key)` 或 Redis 有记录）直接放行，即使已达上限。
3. **5000/10000 与 1000 的实际差别只在"新用户何时被拒"** —— 对一个尚未上线的项目，1000 是纯粹的过早约束。

> **真正的约束是内存**，不是这个数字：单条 QUIC 连接（quinn 流缓冲 + 残包缓冲）约 50~150KB，10000 连接 ≈ 0.5~1.5GB。2C4G 上需自行评估，但**评估的依据应是内存水位，而不是让代码替你做 1000 的判断**。

### 2.3 已知语义（保持，不在本任务改变）

`api.md:518` 已记录：`max_connections` 统计的是 **DashMap 总大小，含全部连接类型**（PC + MOBILE 各平台、text/img/video/file/other 各 `ConnectionType`）。即一个用户多端多连接会占多个名额。本任务只改上限来源，不改这个语义 —— 但 §4 的容量估算按"连接数"而非"用户数"计，配置时需注意。

## 3. 改造设计

### 3.1 `crates/quic_service/src/external/config.rs`

**新增常量**（文件顶部、`ChatNodeConfig` 定义之前）：

```rust
/// 默认最大并发连接数(未在 `app_config.toml` 的 `[quic_server]` 配置时生效)。
///
/// 仅作为新建连接的准入上限, 不做内存预分配; 已存在的连接重连不受此限。
/// 实际承载量仍受机器内存约束(单连接约 50~150KB), 2C4G 下需自行评估。
pub const DEFAULT_MAX_CONNECTIONS: usize = 10000;
```

**`new()` 默认值**（`:31`）：

```rust
-            max_connections: 1000,
+            max_connections: DEFAULT_MAX_CONNECTIONS,
```

**`from_toml_str` 读取配置**（在 `:90` 的 `node_address` 之后、`:92` 的 `server_index` 之前插入）：

```rust
// 最大并发连接数: 未配置/非法(<=0)时回退默认值
let max_connections = quic
    .get("max_connections")
    .and_then(|v| v.as_integer())
    .filter(|v| *v > 0)
    .map(|v| v as usize)
    .unwrap_or(DEFAULT_MAX_CONNECTIONS);
```

并在 `Ok(Self { ... })` 中补 `max_connections,`（与现有的 `cert_path` / `key_path` / `server_name` / `node_address` / `server_index` 同级，仍靠 `..Self::new(bind_address)` 兜其余字段）。

> `.filter(|v| *v > 0)` 是必要的：`as_integer()` 返回 `i64`，负数直接 `as usize` 会回绕成天文数字，等于关掉准入检查。`0` 同样无意义（任何连接都进不来），一并回退。

### 3.2 `config/app_config.toml`

`[quic_server]` 段（`:22-27`）追加一行：

```toml
[quic_server]
address="${QUIC_SERVER_ADDRESS}"
cert_path="./config/ssl/fullchain.pem"
key_path="./config/ssl/privkey.pem"
server_name="${QUIC_SERVER_NAME}"
node_address="${QUIC_NODE_ADDRESS}"
max_connections=10000  # 最大并发连接数(新建连接准入上限, 重连不受限); 未配置默认 10000
```

> **不要写 `${QUIC_MAX_CONNECTIONS}`**：该文件的 `${VAR}` 替换在变量缺失时**静默变空字符串**（`docs/crate-common.md:45` 已记录此坑），空串解析失败会落到默认值 —— 表面能用，实则配置不生效且无告警。要改就直接改数字。

### 3.3 `crates/quic_service/src/external/api.md`（三处）

| 行 | 现状 | 改为 |
|----|------|------|
| `:283` | `pub max_connections: usize, // 最大在线连接数（默认 1000）` | `// 最大并发连接数（[quic_server].max_connections，默认 10000；仅限新建连接，重连不受限）` |
| `:302-309`（TOML 映射块） | 无 `max_connections` 行 | 补 `max_connections = 10000        # 可选，默认 10000；<=0 视为非法回退默认` |
| `:310` | `其余字段（max_connections 等）**只能走默认值**，TOML 中不读取。` | `其余字段（`max_buffer_length`、`idle_timeout_secs` 等）**只能走默认值**，TOML 中不读取。` |

> `:518` 的「含全部类型连接」注记**保留不动**（语义未变）。

### 3.4 测试（`config.rs` 的 `mod tests`）

两处既有断言（`:131`、`:153`）由 `1000` 改为 `DEFAULT_MAX_CONNECTIONS`，并**新增**一个用例：

```rust
#[test]
fn test_from_toml_str_max_connections() {
    // 显式配置时取配置值
    let toml = r#"
[quic_server]
address = "0.0.0.0:4433"
max_connections = 25000
"#;
    let config = ChatNodeConfig::from_toml_str(toml).expect("解析 TOML 配置失败");
    assert_eq!(config.max_connections, 25000);

    // 非法值(0/负数)回退默认值, 避免 usize 回绕成超大上限
    for invalid in ["0", "-5"] {
        let toml = format!(
            "[quic_server]\naddress = \"0.0.0.0:4433\"\nmax_connections = {}\n",
            invalid
        );
        let config = ChatNodeConfig::from_toml_str(&toml).expect("解析 TOML 配置失败");
        assert_eq!(
            config.max_connections, DEFAULT_MAX_CONNECTIONS,
            "非法值 {} 应回退默认", invalid
        );
    }
}
```

## 4. 容量基线（2C4G 纯 SSD 估算）

> 本节是**数量级估算**，用于判断"什么时候必须做优化"，不是承诺值。真实数据以任务 09 的 V4/V7 实测为准。

### 4.1 瓶颈排序

| 资源 | 上限来源 | 量级 |
|------|----------|------|
| **SSD fsync** | 每条消息一次提交（消费级 SSD 0.5~3ms） | 单线程串行 **300~1,000 msg/s**；并发靠组提交摊薄到 **2,000~5,000/s** |
| **CPU** | QUIC 握手（X25519 + AES-GCM ≈ 0.2~1ms/次） | 握手 **1,000~3,000/s**；稳态消息处理 **1~4 万/s** |
| **DB 连接池** | `FastPool` 默认池大小（未显式调大）+ 2s 取连接超时 | 并发 DB 操作受限，**登录风暴时 2s 后开始报错** |
| **RAM** | 单连接 50~150KB + PG + Redis | 理论上万，**由本任务的 `max_connections` 决定策略上限** |

**结论：磁盘 fsync 是最先碰到的墙，不是 CPU、不是连接数。**

### 4.2 三场景估算

**A. 稳态收发**（解密 → bincode → v5 派生 → DashMap 查接收者 → INSERT → 在线则推一帧）

| 形态 | 估算 |
|------|------|
| 现状（逐条 await insert） | **1,000~3,000 msg/s**（fsync 主导） |
| mpsc 批量化后（100 条/次） | **5,000~15,000 msg/s**（转 CPU / 索引维护主导） |

> 每条消息需维护 **4 个索引**（PK、`nano_uk`、`idx_chat_msg_pull`、`idx_chat_msg_recv`），批量写时索引随机更新成为次级瓶颈。

**B. 连接初始化**（QUIC 握手 → JWT → user_info → `user_online` → **`aggregate_user_sessions`**）

| 项 | 估算 |
|----|------|
| 握手本身（CPU 限） | 1,000~3,000/s |
| **含聚合的实际登录** | **200~1,000/s**（数据量小时），随消息表增长退化 |
| 必须扛住的突发 | **500~1,000/s**（App 冷启动 / 网络抖动后的全体重连） |

**C. 推送**（无 DB：DashMap 查连接 + 组帧 + 加密 + 发送）

| 形态 | 估算 |
|------|------|
| 单聊推送 | 与 A 同速（1 推/消息） |
| 群聊扇出 | 1 消息 × N 成员 → **10,000~50,000 帧/s** |

> 群聊在此体现设计价值：**落库只写 1 行**（`session` / `user_session` 分离的收益），成本全在扇出侧的内存操作，无写放大。

### 4.3 周期聚合的天花板（重要）

任务 09 §4 的 30s 周期聚合是**串行遍历在线用户、每人跑一次 V4 跨分区扫描**：

| 在线用户 | V4=30ms 时每轮耗时 | 占空比 |
|---------|------------------|--------|
| 100 | 3s | 10% ✓ |
| 500 | 15s | 50% ⚠️ |
| 1,000 | 30s | 100% ❌ 积压 |

**天花板 ≈ 500 在线用户**（除非 V4 变快）。这正是任务 04b + 任务 09 §2.4 LATERAL 重写要解决的：把聚合从「跨 16 分区扫全部历史消息」降到「按会话点查」，成本可降 1~2 个数量级。

**依赖链：任务 04b → 任务 09 §2.4 LATERAL 重写 → 周期聚合才能撑住规模。**

## 5. 优化触发阈值（可判定）

把散落在任务 03/05/06/09 的性能注记收敛为可判定的动作表：

| 触发条件 | 动作 | 出处 |
|---------|------|------|
| 在线用户数逼近 **500** 且 `session.last_message_at` 明显陈旧 | 下调周期聚合频率（60s/120s）或先做 LATERAL 重写 | 任务 09 §4 / 本文档 §4.3 |
| V4 实测达**秒级** | 启动 LATERAL 重写（前提：任务 04b 已实施） | 任务 09 §2.4 |
| 稳态消息写入持续 **> 1,000 msg/s** 或 PG fsync 明显拖慢 ACK | 启动 mpsc 批量写（10s / 100 条） | 本文档 §4.2-A |
| `/session/list` p95 **> 50ms** | 启动未读数冗余列（逃生通道） | 任务 09 §5 |
| 登录风暴时出现 `2s` 取连接超时错误 | 调大 `FastPool` 池大小 | 本文档 §4.1 |
| 内存水位 > 70% 且连接数接近配置上限 | 下调 `max_connections`（或扩容） | 本文档 §2.2 |

> **个人 IM 的现实负载参考**：200 并发在线、人均 2 分钟一条 ≈ **1.7 msg/s** —— 现有设计有 **100~1,000 倍余量**。上表全部是"未来才可能触发"的阈值，现在无需任何动作。
