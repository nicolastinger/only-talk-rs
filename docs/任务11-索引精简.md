# 任务 11：索引精简（写路径优先）

> 来源：容量评估讨论 + 用户决策「宁愿少点查询索引也要减少一些索引提高写入性能」「不用顾虑任何历史数据」
> 状态：已实施（**依赖任务 02 已实施**：两张消息表已是分区表；与任务 05–10 无耦合，可在任意位置插入）—— 实施记录见 §9
> 定位：把两张消息表的索引 **4+5 压到 2+2**，全部由约束承担、零独立索引。纯 DDL + 少量查询改写，无接口变更

---

## 1. 目标与边界

### 1.1 本任务做什么

| # | 内容 |
|---|------|
| 1 | `chat_message_record`：PK 换序为 `(session_uuid, id)` 并带 INCLUDE，删除两个独立索引（4 → 2） |
| 2 | `group_message_record`：同上，并吸收死索引 `idx_group_msg_send_user`（5 → 2） |
| 3 | 群聊翻历史排序统一到 `id`（消除对 `timestamp` 排序索引的依赖） |
| 4 | 清理任务 `delete_messages_before` 重构为**逐分区 ctid 批删** |
| 5 | 删除死索引 `idx_group_msg_send_user`、死函数 `select_last_by_column` |
| 6 | EXPLAIN 前后对照验证（复用任务 09 的 V1–V7） |

### 1.2 本任务不做什么

| 不做 | 理由 |
|------|------|
| 聚合 LATERAL 重写 | 任务 09 §2.4（前提：任务 04b）。本任务会让 V4 略慢，**强化**其优先级，但不在此实施 |
| 未读数冗余列 | 任务 09 §5，仍以 `/session/list` 实测 p95 决定 |
| 消息批量写（mpsc） | 任务 10 §5 触发阈值；本任务是它的**前置优化**（批写时索引维护是主要放大项） |
| 为历史数据保留任何兼容路径 | 用户明确：无历史数据，DROP 重建即可 |

### 1.3 决策依据

写路径现状：每条消息落库需维护 **4 次索引**（单聊）/ **5 次**（群聊），且都是分区内随机 B-tree 插入 —— 这是 INSERT 除 WAL 外的主要成本，且随分区数线性放大。

读侧对照显示索引与查询**错配**而非单纯冗余：

- 有的索引**无查询使用**（`idx_group_msg_send_user` 全仓无 `send_user` 过滤；`nano_uk` 在单聊表无读查询）
- 有的查询**无索引支持**（`select_chat_by_limit` 双 OR、聚合 `distinct on`、`select_last_by_column`）

既然两张表的**全部热读都钉在分区键上**（`session_uuid` / `group_uuid`），而分区剪枝后已在单分区内，就可以让 PK 一并承担 —— **用约束替代独立索引**。

## 2. 目标 DDL

### 2.1 `chat_message_record`

```sql
CREATE TABLE IF NOT EXISTS chat_message_record (
    id           bigserial   NOT NULL,          -- 自增id(bigserial)
    session_uuid uuid        NOT NULL,          -- 会话标识: 单聊由用户对 v5 派生
    nano_id      varchar(64) NOT NULL,          -- 消息主键(会话内唯一)
    send_user    uuid        NOT NULL,
    recv_user    uuid        NOT NULL,
    text_type    int4        NOT NULL DEFAULT 0,
    "timestamp"  int8        NOT NULL,
    raw          bytea       NULL,
    -- 分区表约束必须含分区键。PK 以 session_uuid 打头, 直接承担同步/未读/最大id 三类热读;
    -- INCLUDE 使窗口过滤与未读计数免回表(Index Only Scan)。
    CONSTRAINT chat_message_record_pk
        PRIMARY KEY (session_uuid, id) INCLUDE (recv_user, "timestamp"),
    CONSTRAINT chat_message_record_nano_uk
        UNIQUE (nano_id, session_uuid)
) PARTITION BY HASH (session_uuid);

-- 16 个哈希分区(同任务02)
DO $$
BEGIN
    FOR i IN 0..15 LOOP
        EXECUTE format(
            'CREATE TABLE IF NOT EXISTS chat_message_record_p%s
             PARTITION OF chat_message_record
             FOR VALUES WITH (MODULUS 16, REMAINDER %s)',
            lpad(i::text, 2, '0'), i);
    END LOOP;
END $$;

-- 任务11: 不再有任何独立 CREATE INDEX
--   (原 idx_chat_msg_pull → PK; 原 idx_chat_msg_recv → PK 的 INCLUDE 列)
```

### 2.2 `group_message_record`

```sql
CREATE TABLE IF NOT EXISTS group_message_record (
    id         BIGSERIAL,
    nano_id    VARCHAR(64) NOT NULL,
    group_uuid UUID NOT NULL REFERENCES group_info(group_uuid),
    send_user  UUID NOT NULL,
    timestamp  BIGINT NOT NULL,
    raw        BYTEA NOT NULL,
    msg_type   SMALLINT DEFAULT 1,
    recalled   BOOLEAN DEFAULT FALSE,
    -- send_user 进 INCLUDE: 群未读计数条件为 send_user <> me, 免回表
    CONSTRAINT group_message_record_pk
        PRIMARY KEY (group_uuid, id) INCLUDE ("timestamp", send_user),
    CONSTRAINT group_message_record_nano_uk
        UNIQUE (nano_id, group_uuid)
) PARTITION BY HASH (group_uuid);

-- 16 个哈希分区(同任务02)
-- 任务11: 删除三个独立索引
--   idx_group_msg_pull       → PK
--   idx_group_msg_group_time → PK(需先把翻历史排序统一到 id, 见 §4.2)
--   idx_group_msg_send_user  → PK 的 INCLUDE 列(该索引原本无任何查询使用)
```

> `nano_uk` 保留的依据：群聊 `select_by_nano_id`（已读桥接，`text_msg_service.rs:87`）是**读查询**直接依赖它；单聊侧则作为去重保险，且是将来 mpsc 批量写 `ON CONFLICT (nano_id, session_uuid) DO NOTHING` 的必要条件。

## 4. 连带改造

### 4.1 清理任务重构（本任务的主要代价）

任务 09 §3.2 的清理依赖 `id` 有索引：

```sql
DELETE FROM chat_message_record WHERE id IN (
    SELECT id FROM chat_message_record WHERE "timestamp" < $1 LIMIT $2)
```

PK 换成 `(session_uuid, id)` 后，外层 `WHERE id IN (...)` **无法用 PK**（前导列是 session_uuid）→ 每个 id 都要全扫 16 分区，退化到不可用。改为**逐分区 ctid 批删**：

```rust
/// 分批删除窗口外消息(任务11: PK 不再以 id 打头, 改为逐分区 ctid 批删)。
///
/// ⚠️ 必须**逐分区**执行: 子查询与删除目标同一分区, ctid 才安全。
///    跨分区 ctid 会误删(主方案 §15.6 陷阱) —— 不可合并为单条语句。
pub async fn delete_messages_before(
    rb: &dyn Executor,
    boundary: i64,
    batch: u32,
) -> Result<u64, rbatis::Error> {
    let mut total = 0u64;
    // 分区名由 DDL 固定(后缀 p00..p15), 直接枚举, 无需查 pg_inherits
    for table in ["chat_message_record", "group_message_record"] {
        for i in 0..16 {
            let partition = format!("{table}_p{i:02}");
            let sql = format!(
                "DELETE FROM {partition} WHERE ctid IN (
                     SELECT ctid FROM {partition}
                     WHERE \"timestamp\" < $1 LIMIT $2)"
            );
            let res = rb.exec(&sql, vec![value!(boundary), value!(batch)]).await?;
            total += res.rows_affected;
        }
    }
    Ok(total)
}
```

> **为何可接受**：清理是**每天一次的后台任务**，扫得起（`timestamp` 无索引 → 分区内 seq scan，`LIMIT` 命中即止），且删的是窗口外数据、只影响少数分区。写路径扛不起第 3、4 个索引，清理任务扛得起扫描 —— 这正是本任务取舍的落点。
>
> 若实测单轮 32 条语句（2 表 × 16 分区）开销明显，可优化为：先按分区判断是否有窗口外数据再删，或把 `timestamp` 之外的分区过滤前置。日频任务，暂无必要。

### 4.2 群聊翻历史排序统一到 `id`

`group_message_record.rs:47`：

```rust
// 改前
"select * from group_message_record where group_uuid = #{group_uuid} order by timestamp desc limit #{size} offset #{start}"
// 改后
"select * from group_message_record where group_uuid = #{group_uuid} order by id desc limit #{size} offset #{start}"
```

三点理由：

1. PK `(group_uuid, id)` 直接支持该排序，无需 `idx_group_msg_group_time`；
2. `id` 是**落库顺序**，即消息真实到达顺序 —— 比客户端生成的 `timestamp` 更权威（producer 时钟不可信）；
3. **消除内部不一致**：群聊同步（`select_unread`）本就按 `id` 排，翻历史却按 `timestamp` 排 —— 两套顺序各养一个索引，且客户端看到的顺序可能不同。

> 客户端影响：`/group/chat/message/history` 返回顺序由时间序变为 id 序。二者绝大多数情况一致（id 随插入递增）。**已知边界**：批量写入（任务 10 的 mpsc）会让同一批内 id 顺序与 timestamp 顺序解耦 —— 此时 id 序仍是正确的到达顺序。

新增两条针对本任务的验证：

```sql
-- V8: 群翻历史(改排序后) —— 期望 PK 索引扫描, 无 Sort 节点
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM group_message_record
WHERE group_uuid = '...' ORDER BY id DESC LIMIT 20 OFFSET 0;

-- V9: 索引体积对照 —— 确认 INCLUDE 加宽未导致索引膨胀失控
```

> V9 是本任务的关键观测：**用 2 个「宽」索引换 4+5 个「窄」索引**，净收益要看总体积与写放大。理论上索引维护次数减半即为净赚，但 INCLUDE 列会让叶页变大，需实测确认没有意外膨胀。

- **无需任何迁移脚本** —— 未上线、无历史数据（用户明确）。
- 开发库手动执行一次（与任务 02 同款）：

```sql

DROP TABLE IF EXISTS group_message_record CASCADE;
```

- **DDL 文件保持幂等**：仍用 `CREATE TABLE IF NOT EXISTS` + `DO $$` 分区循环，满足 CD 每次重放的要求（`apply_all_ddl` 按文件名顺序全量执行）。
- ⚠️ **`CREATE TABLE IF NOT EXISTS` 不会修改已存在的表** —— 已建分区表的开发库必须 `DROP` 重建，否则改动静默不生效（主方案 §15.5 记录的陷阱）。重建动作以注释形式写在 DDL 文件头部，与任务 02 保持一致。
