## 2. 问题回顾（为什么 v1 不够）

任务 05/07 已实施的形态：`mode: incremental|initial` + 增量起点取**服务端 `user_session.synced_id`**（用户级，全设备共享）。多端场景下：

```
手机读到 2988 离线 → PC 同步过 → 服务端 synced_id = 5230
手机重连 → incremental → id > 5230 → 空响应 → 一轮终止
→ 2989–5220 手机永远拿不到(除非点开会话漫游), 且 unread 已被 PC 的已读清零
```

v1（本档前一版）的解法是「initial 支持向旧翻页 + 客户端缺口检测」，但保留了 `mode` 与「服务端游标权威」的概念，服务端仍维护两套查询语义。

**无包袱重设计的洞察**：问题根源是「拉取起点取自服务端的用户级游标」。而设备本地的缺口信息**只有设备自己知道**（本地 `synced_id` 落后服务端多少，服务端无从得知）。因此把拉取起点交给客户端显式携带，问题从根上消失：

> **拉取 = 无状态窗口查询（客户端自带游标）；状态 = 客户端本地（缺口真相所在地）**
> 服务端游标（`synced_id`）只保留**回报**方向的角色（钳制已读），不再参与拉取。

### 2.1 心智模型：Kafka 消费者（用户定）

**会话 = topic，设备 = 消费者组，消费水位由消费者（设备）本地维护** —— v2 与 Kafka 消费模型同构：

| Kafka | 本设计 |
|---|---|
| topic（顺序域）| 会话（会话内 `id` 单调 = offset）|
| 消息 offset | `chat_message_record.id`（bigserial，追加时分配）|
| 消费者组（各组独立消费全量）| **设备** —— 各设备补自己的洞，互不干扰（多端语义的根源）|
| 消费者 poll（拉）| `/session/sync` 拉取（客户端游标 = fetch 位置）|
| 位移提交（commit）| `/session/synced` 回报 + 本地 `session_sync_state.synced_id` |
| seek / 回放 | 同意式 10 条 + 回填（seek 到最新后向旧回放；`hist_floor` = 回放记账）|
| 日志保留（默认 168h）| 7 天窗口 + 每日清理（`truncated_by_window` = OffsetOutOfRange）|
| at-least-once + 幂等消费 | 宁重勿漏 + nano_id 去重 |

**三处有意偏差（非疏漏）**：

1. **服务端 `user_session.synced_id` 是「用户级取最大」的 commit** —— Kafka 各组独立提交、broker 不据此重投；我们同样不据此重投（拉取起点在客户端），它唯一的职责是钳制已读（`last_read_id <= synced_id`），实现「任一端送达即视为已送达」的未读语义。
2. **双通道分域（用户定，架构不变式）** —— Kafka 纯拉；我们是**领域不相交的双通道**：**QUIC 只管在线实时投递，离线补齐永远走 HTTP 拉取**。推送不带 offset 因此不是待弥合的缺陷 —— 它不承担投递完整性，无需 offset；任何断连窗口的消息一律由拉取域从 `synced_id` 起补齐，在线期已收过的被**自然重放**（宁重勿漏），副作用恰好把 `server_id` 附上去。**禁止**将来加「重连时 QUIC 推送离线积压」—— 看似省一次 HTTP 往返，实则制造双投递路径，重放/去重/游标推进全要在推送域重做。原则：**推送管在线实时，拉取管离线完整**。
3. **本地保留 > 服务端保留** —— 消费者本地库（SQLite）是比 broker（7 天清理）更长久留的物化副本，漫游回退本地即此语义。

**该模型反向印证的两件事**：① v1 的 bug 本质 = 两台设备共享同一个组位移（Kafka 中不存在的配置），v2 即还回组边界；② 集群演进三段式（任务 10）的终点 —— Kafka 分区的本质是**顺序域**，跨节点乱序不可接受时按 `session_uuid` 分区即本模型的完全体。

## 3. 协议设计（服务端）

### 3.1 契约

```
POST /session/sync
Headers: Authorization: <jwt>

{
  "sessions": [
    { "session_uuid": "3f2b..." },                  // 首拉: 窗口内最新 limit 条
    { "session_uuid": "9a1c...", "before_id": 5221 } // 续拉: 窗口内 id < 5221 的最新 limit 条
  ],
  "limit": 10
}
```

```json
{
  "code": 200,
  "data": {
    "server_time": 1758000000000,
    "sessions": [
      {
        "session_uuid": "3f2b...",
        "session_type": 1,
        "messages": [ /* id 升序 */ ],
        "next_cursor": 5230,          // 本批最大 id(回报 synced_id 用; 命名沿用已交付 VO)
        "has_more": false,            // 窗口内是否还有更旧消息
        "truncated_by_window": true   // 更旧消息存在但已出 7 天窗口
      }
    ]
  }
}
```

### 3.2 语义表（写死，避免实现歧义）

| 语义 | 规则 |
|------|------|
| 查询形态 | **唯一一种**：`session_uuid = ? AND id < before AND "timestamp" > boundary ORDER BY id DESC LIMIT k+1`；`before` 缺省取 `i64::MAX`（id 永达不到，等价无上界） |
| 消息顺序 | 响应内 `id` **升序**（取前 k 条后反转）—— 与已交付契约一致 |
| `has_more` | `limit+1` 探测（返回第 k+1 条存在即 true）—— 即「窗口内还有更旧消息」 |
| `next_cursor` | 本批**最大** id。客户端拉取成功后经 `/session/synced` 回报 —— `synced_id` 语义为「已确认前沿」（用户级），与本地历史洞正交 |
| `truncated_by_window` | **仅 `has_more=false` 时**探测：`EXISTS (id < 本批最小 id)` —— 更旧消息存在且不在窗口内（窗口内已被 `has_more=false` 排除）→ true。比 v1 的 timestamp 比较探测更简 |
| 归属校验 | 请求中每个 session 查 `user_session(me, session_uuid)` 行：无行 → **静默跳过**（warn 日志），不报错 —— 兼容「聚合未跑/已退群」边界，且不泄露会话存在性 |
| `session_type` | 取自 `user_session` 行（1-单聊走 `chat_message_record`，2-群聊走 `group_message_record`，`recv_user=group_uuid`，`text_type=msg_type`）—— 归属校验的同一次查询顺带取出，**零额外成本** |
| 窗口 | 服务端算（`timestamp > now - 7d`），不信任客户端时钟 |
| limit | clamp `[1, 200]`，默认 100 |
| 空 `sessions` | **不支持**（v1 遗留语义删除）—— 客户端始终显式携带要拉的会话（缺口检测的产物） |

### 3.3 与 v1（已交付形态）的协议差异

| 项 | 已交付（任务05） | v2（本任务） |
|----|-----------------|--------------|
| `mode` | `incremental` \| `initial` | **删除** |
| 拉取起点 | 增量=服务端 `synced_id`；initial=最新 | **客户端显式**（`before_id` / 隐含最新） |
| 空 `sessions` | 服务端筛「有未同步」会话 | 不支持，客户端必须携带 |
| 服务端状态依赖 | `user_session.synced_id`（拉取选择） | 仅 `user_session` 行存在性（归属校验） |
| 查询代码路径 | 增量 / initial 两套 | **一套**（向后翻页） |

> **为什么敢删 `mode`**：区分「增量 / 首拉」的本意是「新消息追赶 vs 新设备初始化」。v2 里两者是**同一种查询**（最新 N 条，向旧翻页），区别只在于客户端从哪个缺口开始、拉多少 —— 全在客户端本地状态里，服务端无需区分。**「增量」概念是服务端游标权威的产物，删掉权威，它就没了存在必要。**

## 4. 客户端流程（任务 07 侧重写）

### 4.1 重连主流程

```
QUIC 连接成功(user_online 触发服务端聚合 —— 见 §4.4 新鲜度说明)
   │
   ├─ 1. refresh_session_list()        → /session/list 全量翻页
   │       落库: last_message_id / last_message_at / last_preview
   │             / unread / pinned / muted / session_uuid
   │
   ├─ 2. 缺口检测(本地, 零请求, 跨域比较):
   │       gap = { s | s.last_message_id(会话域) > s.synced_id(同步域) }
   │
   ├─ 3. 静默补拉(自动, 不弹窗; 建批 batch_id=now, 每缺口会话一条任务行):
   │       POST /session/sync { sessions: gap(无 before_id), limit: 10 }
   │       落库(nano_id 去重) → 回报 synced_id → 同步域双写:
   │       任务行(归属本批, status=成功) + 水位表(synced_id=next_cursor;
   │       hist_floor=min(既有, 本批最小 id))  [首次拉取即建立连续前沿]
   │       —— 流量 ~10条×会话数(KB级); 同时把 server_id 附到
   │          QUIC 期收到的消息上, 已读上报由低估自愈(任务07 §5.1)转准确
   │
   └─ 4. 列表刷新完成 → 前端渲染(角标来自服务端 unread)
```

> **方案决策点（默认 A）**：
>
> - **A（默认，推荐）**：10 条最新**静默自动**拉取，弹窗只出现在**进入会话时的 7 天回填确认**。理由：10 条/会话流量是 KB 级，弹窗成本高于流量成本；且静默补拉兼任「server_id 附着 + 已读自愈」两个修复动作，本来就该每次重连都做。真正的流量大头（7 天全量回填）保留用户确认 —— 这才是值得弹窗的门。
> - **B（原讨论形态）**：第 3 步也弹窗询问（"有 N 个会话有未同步消息，是否同步？"）。协议与代码路径完全相同，仅多一个前端确认环节 —— 若产品要严格的流量门控选 B，把 §6 的事件 `session_sync_gap` 接上即可。
>
> 两案共用本文档全部协议与服务端代码，**不构成返工**。

### 4.2 进入会话：7 天回填（同意式，可恢复）

**先讲为什么需要 `hist_floor`**（v2 初稿的教训）：终止条件「本批零新增 = 接上本地历史」在两类场景下**提前误终止** —— ① 回填被中断后从顶重启，首批全在本地即终止，洞留存；②「QUIC 三明治」（本地 = {在线收的一摊, 离线缺口, 又在线收的一摊}），翻到上方 QUIC 块时整批零新增即终止。零新增证明的是「这批在本地」，**不是「下面没洞」**。

修复 = 持久化**连续前沿** `hist_floor`：

> **不变式（由查询构造保证）**：每批拉的是 `before_id` 之下最高的 k 条 → 批内连续且与上方衔接 → 落库后 `hist_floor = 本批最小 id`。
> 推论：一切 `id ≥ hist_floor` 的会话消息都在本地；floor **单调只向下**；新消息只会出现在 floor 上方 → **静默补拉/在线推送永不制造新洞** → `sync_task.backfill = 完成` 一经置位长期有效。

```rust
/// 回填任务执行体(§4.6 worker 调用; 前端确认后经 backfill_session 命令入队)。
/// 从 hist_floor 续翻 —— 中断恢复零成本, 且不存在"重启从顶"的误终止。
pub async fn backfill_session(session_uuid: String) -> Result<(), anyhow::Error> {
    const BACKFILL_LIMIT: u32 = 50;
    // 连续前沿; NULL(从未拉取)时从本地最新位置起步(防御分支, 正常流程静默补拉已建立)
    let mut before_id = get_hist_floor(&session_uuid).await?
        .unwrap_or_else(|| local_last_message_id(&session_uuid));
    if before_id <= 0 { return Ok(()); }

    loop {
        let body = serde_json::json!({
            "sessions": [{ "session_uuid": session_uuid, "before_id": before_id }],
            "limit": BACKFILL_LIMIT,
        });
        let sync = post_sync(&body).await?;
        let Some(s) = sync.sessions.first() else { break };

        for msg in &s.messages {
            insert_sync_message(msg).await?;   // 去重链落库(重复由 nano_id 吸收)
        }
        // 无论本批是否新增, floor 一律压到批最小 id —— 走穿"本地已有"的区域
        // 正是修复误终止的关键: 零新增不再是终止信号, 只是继续向下
        if let Some(min_id) = s.messages.first().map(|m| m.id) {
            before_id = min_id;
            set_hist_floor(&session_uuid, min_id).await?;
        }

        // 终止条件(满足其一) —— 只两条, 不含"零新增":
        if !s.has_more { break; }              // 窗口内已到头(配合 truncated 提示)
        if s.truncated_by_window { break; }    // 更早的已出 7 天窗口
    }
    // 走到窗口底/截断 → 任务完成(不再提示由 sync_task.backfill 派生, 见 §4.6; 新洞不可能形成)
    complete_backfill(&session_uuid).await?;
    Ok(())
}
```

> **中断恢复**：续翻指针**单一载体** —— 水位表 `hist_floor`（无双写无漂移）；进程任意时刻中断，重启时执行中任务行复位为待执行、worker 从 floor 续跑，无回退。
>
> **完成后重进**：水位 `backfill = 完成` → 不再弹提示；即使仍调用，也只是**一次请求** —— floor 已在窗口底，服务端 `!has_more` 立即终止。
>
> **成本权衡**：删除「零新增」终止意味着首次回填要**走穿本地已有的 QUIC 块**（整批去重、零新增照走）—— 多几次请求，换正确性；floor 持久化后这段路每个会话只走一次。

### 4.3 首次登录（全新本地库）

refresh 返回全部会话、`synced_id` 全 0 → 全部是缺口 → 走 §4.1 同一条路径（静默 10 条 + 进会话回填）。**无需任何首登专用分支** —— v1 依赖 `has_any_synced_session()` 区分 initial/incremental，v2 里这个函数连同概念一起删除。

### 4.4 两个已知边界（接受并记录）

**① 聚合新鲜度竞争**：缺口检测依赖 `session.last_message_id`（聚合值）。`user_online` 会异步触发本用户的聚合（任务 03 接线），客户端 refresh 与聚合 spawn 之间存在小竞争 —— refresh 早于聚合完成时，最后几秒的消息可能漏检。**自愈路径**：下次重连 / 30s 周期兜底聚合后重 refresh。原 v1 自动循环从消息表直读不受此影响，但 v1 的缺口检测同样依赖聚合值 —— 此边界非 v2 退步，是「检测驱动」模式共有的性质。

**② QUIC 送达但 synced_id 滞后 → 缺口检测「假阳」**：在线期收到的消息（无 server_id）不推进本地 `synced_id`，重连时这些会话会被检出为缺口。**这不是浪费**：静默补拉会把 server_id 附着上去，已读上报从低估转准确（任务 07 §5.1 自愈机制的触发器）。方案 A 把这个「假阳」变成了收益。

**③ 服务端 at-most-once 丢失对客户端不可见**：消息 ACK 后未落库（既定取舍）→ 任何端从未有过它 → 断链/floor 均无从探测。本地库是「诚实」的（有的都有、丢的不装），但丢了就是丢了 —— 与整个系列的丢失哲学一致，不为此增加机制。

### 4.6 三域职责分离与同步域两表（水位 + 批次记录）

**分离原则**（用户定）：会话表只管会话、聊天记录表只管聊天记录、任务执行表管任务执行。据此重新归位：

| 域 | 表 | 归属内容 | 本次变化 |
|----|----|---------|---------|
| 会话域 | `chat_session` | 展示属性（未读/摘要/置顶/显隐/对方）+ 会话事实（`last_message_id`/`last_message_at` —— 来自 `/session/list`，是**会话的属性**） | 加 `last_message_id`；**删 `synced_id` 列**（它不是会话属性，是拉取执行位置） |
| 消息域 | `chat_record` / `group_chat_record` | 消息本体 + `server_id`（**消息的属性**：消息在服务端的身份，被已读上报消费属跨域读） | 不动 |
| 同步域 | `session_sync_state` + `sync_task`（新，两表） | **水位表**：拉取位置（`synced_id`/`hist_floor`）+ 回填完成态 —— 每会话一行的**持久**状态；**任务表**：执行记录（**批次 × 会话，append**）—— 一次触发一批，整批成败可见 | 新建两表，吸收会话表迁出的位置列 |

> **为什么两表**：批次记录按触发 append、按保留策略清理；位置与回填完成态必须**长存**（提示抑制、续翻、缺口检测都依赖它）。记录会清、状态不清 —— 同表共存就会互相绑架，拆开各自自由。

```sql
-- 水位表: 同步域的每会话持久状态(不随批次清理)
CREATE TABLE IF NOT EXISTS session_sync_state (
    session_uuid TEXT PRIMARY KEY,
    synced_id    INTEGER NOT NULL DEFAULT 0,  -- 前沿: 已回报的最大服务端 id(拉取执行结果)
    hist_floor   INTEGER DEFAULT NULL,        -- 连续前沿: 一切 id ≥ floor 的会话消息都在本地(不变式载体, §4.2)
    backfill     INTEGER NOT NULL DEFAULT 0,  -- 0-未回填过 1-完成 2-跳过(「不再提示」) —— 提示抑制的持久位
    updated_at   INTEGER NOT NULL
);

-- 任务表: 执行记录(批次 × 会话, append)
-- batch_id = 触发时刻毫秒 —— 一次触发(重连轮/同意回填/手动)即一批, 批的成败由聚合派生
CREATE TABLE IF NOT EXISTS sync_task (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    batch_id     INTEGER NOT NULL,            -- 批次=触发时刻(ms), 自带时间语义
    session_uuid TEXT NOT NULL,
    kind         INTEGER NOT NULL,            -- 0-静默补拉(重连轮) 1-回填
    status       INTEGER NOT NULL DEFAULT 0,  -- 0-待执行 1-执行中 2-成功 3-失败
    batches      INTEGER NOT NULL DEFAULT 0,  -- 本任务已消化拉取批次数
    new_count    INTEGER NOT NULL DEFAULT 0,  -- 本任务累计新增消息数
    attempt      INTEGER NOT NULL DEFAULT 0,  -- 重试次数
    last_error   TEXT DEFAULT NULL,           -- 最近失败原因(诊断; 成功时清空)
    created_at   INTEGER NOT NULL,
    updated_at   INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_sync_task_batch   ON sync_task(batch_id);
CREATE INDEX IF NOT EXISTS idx_sync_task_pending ON sync_task(kind, status);
```

**设计决定：**

1. **批次 = 触发事件，`batch_id` 即触发时刻毫秒** —— 一次断线重连 / 一次同意回填 = 一批。「这批整体成功没」= `GROUP BY batch_id` 聚合（总数/成功数/失败数/是否全终态），**不存冗余计数字段** —— 存储的计数与真实任务行迟早漂移，聚合永远是真的。批次头表也不建（其字段全部可由任务行派生）。`get_sync_history` 命令（§6.1）把该视图交给前端 —— 「清晰可见」的落点。
2. **水位与记录分表** —— 位置（`synced_id`/`hist_floor`/回填完成态）是持久的每会话状态，必须**免疫批次清理**；`sync_task` 是 append 记录，按批保留（见 4）。同表共存则记录的清理策略会绑架状态的寿命 —— 拆开后各自自由。
3. **队列 = 任务行本身** —— 回填待执行/执行中即 `kind=1, status∈{0,1}` 的行，worker 按 `id` 序领取（先入队先回填）；入队前查重（已有 pending 不重复入队）。**提示抑制用水位表 `backfill` 列**（持久），不用任务行存在性（记录会清，完成态必须长存）。应用启动时 `UPDATE sync_task SET status=0 WHERE status=1`（进程死亡复位）。
4. **保留最近 50 批（有界）** —— 启动时仅清理「全终态且早于第 50 新批次」的任务行；**pending/running 行永不清理**（队列本体）。水位表每会话一行，永不清理。
5. **唯一的有意跨域读 = 缺口检测**：`chat_session.last_message_id`（会话事实）vs `session_sync_state.synced_id`（执行位置）—— 「服务端说会话到哪了 vs 我拉到哪了」。除此外三域互不读对方内部状态。

**各流程与同步域的关系：**

| 流程 | 动作 |
|------|------|
| 重连静默轮（§4.1） | 建批（`batch_id=now`, kind=0）：每缺口会话一条任务行 → 逐会话执行（单请求 10 条）→ `status=2/3`；水位表 `upsert_pull_position`（`synced_id`/`hist_floor` 推进） |
| 进会话提示（§6.2） | 水位 `backfill==0` 且无 `kind=1, status∈{0,1}` 任务行才弹；有则显进度 |
| 用户同意 | 建批（kind=1）+ 任务行 `status=0` 入队 |
| 「不再提示」 | 水位表 `backfill=2`（任务行不动） |
| worker | 按 `id` 领取 kind=1 pending → 逐批 `record_batch`（floor 压到批最小、`batches`+1、`new_count` 累加）→ 成功：任务 `status=2` + 水位 `backfill=1`；失败：`attempt`+1、`last_error` 落库 |
| `get_sync_history` | `GROUP BY batch_id` 聚合 + 各批任务明细 |

> **进度事件**：worker 每完成一批发 `session_backfill_progress`（§6.2），前端可做"同步中 x 条"提示。

> **列迁移（无包袱直迁）**：`chat_session.synced_id` 已随任务 07 交付 —— 升级路径一条语句：`INSERT INTO session_sync_state(session_uuid, synced_id, updated_at) SELECT session_uuid, synced_id, <now> FROM chat_session WHERE synced_id > 0`，随后 `ALTER TABLE chat_session DROP COLUMN synced_id`（SQLite 3.35+，Tauri 自带版本满足）。`ChatSession` 结构体、`set_session_sync_cursor` 及各构造点同步摘除该字段（rg 复核零残留）。

## 5. 多端场景推演（验收核心，v1 的原始动机）

```
B(手机)读到 2988 离线; A(PC)同步推进服务端 synced_id 至 5230
B 重连:
  增量循环已不存在 —— 无"空响应提前终止"问题
  refresh: last_message_id=5230(假设无更新) → 缺口: 5230 > 本地 synced 2988 ✓
  静默补拉: 拿到 5221–5230, 回报 synced 5230; 角标=服务端 unread(2242, 未读语义正确)
B 打开会话:
  看到最新10条 + 旧2988↓ 之间有断档 → 前端提示"同步最近7天消息?"
  确认 → 入队回填任务(worker 后台消化): 5220←…←2989 逐批落库,
  走穿本地已有区域, 直至窗口底/截断终止 —— 中断重启也续跑
  读到底上报 5230 → 全端角标清零
全程 nano_id 去重, 无重复; 拉取起点是 B 自己的本地位置, 与 A 推进服务端游标无关
```

> **A 设备全程不受影响**：A 已在 5230，A 的 refresh 无缺口，A 不拉任何东西。这正是「拉取起点客户端化」的意义 —— 每台设备补**自己的**洞，互不干扰，服务端游标只是被回报推进的公共前沿。
