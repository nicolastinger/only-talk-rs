> 来源：2026-09-17 讨论定稿；同日按「**无历史包袱**」前提重设计（v2，替代 v1 的「增量改造」形态）
> 状态：已实施（**依赖任务 05、07 已实施**）—— 实施记录见 §9
> 定位：把「服务端游标驱动的自动循环同步」重设计为「**客户端游标驱动的正向追平**」，从根上消灭多端游标互踩问题。服务端 `/session/sync` 重写为**无状态窗口查询**，客户端同步流程整体重构。

## 2. 问题回顾（为什么 v1 不够）

任务 05/07 已实施的形态：`mode: incremental|initial` + 增量起点取**服务端 `user_session.synced_id`**（用户级，全设备共享）。多端场景下：

```
手机读到 2988 离线 → PC 同步过 → 服务端 synced_id = 5230
手机重连 → incremental → id > 5230 → 空响应 → 一轮终止
→ 2989–5220 手机永远拿不到(除非点开会话漫游), 且 unread 已被 PC 的已读清零
```

**无包袱重设计的洞察**：问题根源是「拉取起点取自服务端的用户级游标」。而设备本地的缺口信息**只有设备自己知道**。因此把拉取起点交给客户端显式携带，问题从根上消失：

> **拉取 = 无状态窗口查询（客户端自带游标）；状态 = 客户端本地（缺口真相所在地）**
> 服务端游标（`synced_id`）只保留**回报**方向的角色（钳制已读），不再参与拉取。

### 2.1 心智模型：Kafka 消费者（用户定）

**会话 = topic，设备 = 消费者组，消费水位由消费者（设备）本地维护** —— 与 Kafka 消费模型同构：

| Kafka | 本设计 |
|---|---|
| topic（顺序域）| 会话（会话内 `id` 单调 = offset）|
| 消息 offset | `chat_message_record.id`（bigserial，追加时分配）|
| 消费者组（各组独立消费全量）| **设备** —— 各设备补自己的洞，互不干扰 |
| 消费者 poll（拉）| `/session/sync` 正向拉取（`after_id` = fetch 位置）|
| 位移提交（commit）| `/session/synced` 回报 + 本地 `max(server_id)`（本地前沿即 fetch 位置）|
| 日志保留（默认 168h）| 7 天窗口 + 每日清理（`has_more=false` = 追平或窗口尽头）|
| at-least-once + 幂等消费 | 宁重勿漏 + nano_id 去重 |

> **与 Kafka 的差异（有意，非疏漏）**：① 服务端 `user_session.synced_id` 是「用户级取最大」的 commit，不据此重投（拉取起点在客户端），唯一职责是钳制已读（`last_read_id <= synced_id`）；② **双通道分域（架构不变式）**：QUIC 只管在线实时投递，离线补齐永远走 HTTP 拉取；在线期已收过的消息被**自然重放**（宁重勿漏），副作用恰好把 `server_id` 附上；③ 本地保留 > 服务端保留（7 天清理后本地仍是更久留的物化副本）。

## 3. 协议设计（服务端）

### 3.1 契约

```
POST /session/sync
Headers: Authorization: <jwt>

{
  "sessions": [
    { "session_uuid": "3f2b...", "after_id": 2988 },  // 正向起点: 窗口内 id > 2988 的消息
    { "session_uuid": "9a1c..." }                     // 缺省 = 0(从窗口内最早起, 首次登录/全新会话)
  ],
  "limit": 100
}
```

```json
{
  "code": 200,
  "data": {
    "server_time": 1758000000000,
    "sessions": [
      {
        "session_uuid": "3f2b...",
        "session_type": 1,
        "messages": [ /* id 升序: 2989..2998 */ ],
        "next_cursor": 2998,          // 本批最大 id(= 末条 id; 空批 = 请求的 after_id)
        "has_more": true              // 窗口内是否还有更多(limit+1 探测)
      }
    ]
  }
}
```

### 3.2 语义表（写死，避免实现歧义）

| 语义 | 规则 |
|------|------|
| 查询形态 | **唯一一种**：`session_uuid = ? AND id > after AND "timestamp" > boundary ORDER BY id ASC LIMIT k+1`；`after` 缺省取 `0` |
| 消息顺序 | 响应内 `id` **升序**（正向取，天然有序，无需反转）|
| `has_more` | `limit+1` 探测（返回第 k+1 条存在即 true）—— 即「窗口内还有更新消息」 |
| `next_cursor` | 本批**最大** id（= 末条 id）；空批 = 请求的 `after_id`。客户端以此续拉，追平后经 `/session/synced` 回报 |
| 停止条件（客户端） | `messages` 空 或 `has_more=false` —— 已追平服务端最新 id，或到达 7 天窗口尽头（窗口由 `boundary` 过滤天然达成，无独立截断标志）|
| 归属校验 | 请求中每个 session 查 `user_session(me, session_uuid)` 行：无行 → **静默跳过**（warn 日志），不报错 —— 兼容「聚合未跑/已退群」边界，且不泄露会话存在性 |
| `session_type` | 取自 `user_session` 行（1-单聊走 `chat_message_record`，2-群聊走 `group_message_record`，`recv_user=group_uuid`，`text_type=msg_type`）|
| 窗口 | 服务端算（`timestamp > now - 7d`），不信任客户端时钟 |
| limit | clamp `[1, 200]`，默认 100 |
| 空 `sessions` | 返回空响应（客户端始终显式携带要拉的会话）|

### 3.3 与旧形态的协议差异

| 项 | 旧 v2（任务12 前版） | 现版（正向追平） |
|----|---------------------|-----------------|
| `mode` | 已删除 | 已删除 |
| 拉取起点 | `before_id`（向后翻页，缺省 = 最新） | **`after_id`**（正向追平，缺省 = 0 = 窗口内最早起） |
| 消息顺序 | 服务端取降序后**反转**升序 | 直接升序 |
| 窗口尽头信号 | `truncated_by_window`（`exists_older_than` 探测）| **删除** —— `has_more=false` 即「追平或窗口尽头」 |
| 客户端缺口检测 | `chat_session.last_message_id > session_sync_state.synced_id` | **删除** —— 直接比较「服务端目标 `last_message_id` vs 本地前沿 `max(server_id)`」 |
| 连续前沿 | `session_sync_state.hist_floor`（向后走穿的记账）| **删除** —— 正向连续拉取天然无洞 |
| 同意式回填 | `sync_task` 队列 + worker + `backfill` 命令 | **删除** —— 重连即自动正向追平到最新/窗口尽头 |

### 3.4 服务端 delta 清单

| 位置 | 动作 |
|------|------|
| `session_service/dto.rs` | `SyncSessionReq { session_uuid, #[serde(default)] after_id: Option<i64> }`（原 `before_id`）；`SyncSessionVO` 删 `truncated_by_window` |
| `session_service/service.rs` | `sync_sessions` 单路径：归属校验 → `select_window_after(after, boundary, limit+1)` → 取 limit 条（升序）→ `has_more` 探测 → `next_cursor`=末条 id（空批=`after`） |

| `entity/.../user_session.rs` | `select_by_user_and_session(me, session_uuid)`（归属校验 + session_type，已就位） |
| 测试 | §7.1 重写（正向语义）|

> **索引零改动**：`select_window_after` 是 `session_uuid` 等值 + `id` 范围 + `timestamp` 过滤 —— 任务 11 的 PK `(session_uuid, id) INCLUDE (recv_user, "timestamp")` 直接支持，Index Only Scan。

## 4. 客户端流程

### 4.1 重连主流程（正向追平）

```
QUIC 连接成功
   │
   ├─ 1. refresh_session_list()        → /session/list 全量翻页
   │       服务端首页惰性聚合(偏差记录 §1.7) → last_message_id 即每会话服务端最新 id
   │       落库: last_message_id / last_message_at / last_preview
   │            / unread / pinned / muted / session_uuid
   │
   └─ 2. sync_sessions_forward(串行逐会话):
           mine   = 本地前沿 max(server_id)   (单聊按对端 / 群聊按 group)
           target = s.last_message_id
           target <= mine → 跳过(已追平)
           loop:
             POST /session/sync { session_uuid, after_id: mine, limit: 100 }
             messages 空 → 停(追平)
             落库(nano_id 去重 + 回填 server_id) → after = next_cursor
             !has_more → 停(追平服务端最新 或 7 天窗口尽头)
           每会话追平后回报 POST /session/synced { synced_id: after }
```

- **串行**：一个会话一个会话拉完再下一个（用户指定），简单可观测。
- **目标值来源**：`/session/list` 的 `last_message_id`（服务端聚合结果，登录/重连时必然新鲜）。
- **本地前沿**：`chat_record.server_id` / `group_chat_record.server_id` 的 `MAX`。在线期 QUIC 消息无 `server_id`（NULL）→ 不计入前沿 → 下次重连被检出为增量 → 重拉去重（nano_id）+ 回填 `server_id` → **前沿自愈**（同时让已读上报从低估转准确）。

### 4.2 首次登录（全新本地库）

`mine` 全为 0（无本地消息）→ 每个会话从 `after_id=0` 正向拉取，直到 `has_more=false` —— 即把 7 天窗口内全部消息按序补齐。**无需任何首登专用分支**。

> **数据量注记**：正向追平会拉全窗口内每条消息（旧设计的静默补拉只拉最新 10 条）。首次登录/长期未同步时单会话可能数千条、多会话串行耗时 —— 这是换取极简逻辑的既定取舍（用户确认）。上限即 7 天窗口 × 会话消息密度。

### 4.3 两个已知边界（接受并记录）

**① 聚合新鲜度竞争**：追平目标依赖 `session.last_message_id`（聚合值）。`refresh_session_list` 首页惰性聚合与客户端请求之间存在竞争窗口 —— refresh 早于聚合完成时，最后几秒的消息可能漏检。**自愈路径**：下次重连重新 refresh 后重拉（漏检会话 `target` 未变但本地有增量，或 target 已更新）。

**② QUIC 送达但无 server_id → 增量「假阳」**：在线期收到的消息不计入本地前沿，重连时这些会话被检出为增量。**这不是浪费**：重拉把 `server_id` 附着上去（去重 + 回填），已读上报从低估转准确 —— 假阳被转化为收益。

**③ 服务端 at-most-once 丢失对客户端不可见**：消息 ACK 后未落库（既定取舍）→ 任何端从未有过它 → 无从探测。本地库是「诚实」的，丢了就是丢了 —— 与整个系列的丢失哲学一致。

## 5. 多端场景推演（验收核心）

```
B(手机)读到 2988 离线; A(PC)已推进服务端 synced_id 至 5230
B 重连:
  refresh: last_message_id=5230 → 本地前沿 mine=2988 → 增量 ✓
  正向追平: after_id=2988 → 2989..3088 → ... → 5230, has_more=false 停

A 设备全程不受影响: A 的本地前沿=5230, target 无更新 → 无增量, 不拉任何东西
全程 nano_id 去重, 无重复; 拉取起点是 B 自己的本地位置, 与 A 推进服务端游标无关
```

## 10. 修订记录：为什么砍掉「向后翻页 + hist_floor + 同意式回填」

正向追平取代旧设计的关键论证：

1. **正向连续拉取天然无洞**。旧的向后翻页从「顶部最新」往下走，本地已收的 QUIC 块会造成「零新增但下面有洞」的误终止，才需要 `hist_floor` 连续前沿来记账。正向拉取从客户端本地前沿（`max(server_id)`）开始**严格向上**延伸，每批接在上一批末尾 —— 落库后本地前沿自动连续，**不存在洞**，`hist_floor` 与「走穿本地块」的复杂度整体消失。
2. **同意式回填失去存在前提**。7 天回填的本质是「向旧补齐本地缺失的历史」；正向追平在重连时就把窗口内消息全部补齐（`has_more=false` 即窗口尽头），历史由拉取路径自动覆盖，不再需要「进会话确认 + 后台 worker + 任务队列」。
3. **本地前沿本身可推导**。旧设计用 `session_sync_state.synced_id` 单独记账拉取位置；新设计用消息表自带的 `server_id` 直接 `MAX()` 推导 —— 少一张状态表，且与已读上报（任务 07 同样用 `max(server_id)`）共享同一事实，无双写漂移。
4. **在线期消息无 server_id 的「假阳」成为收益**：重拉去重 + 回填 `server_id` 恰好完成自愈。

> `session_sync_state` + `sync_task` 两表因此**保留休眠**（未上线无迁移成本；若将来引入「进会话才拉历史」的节流策略可复用其结构）。
