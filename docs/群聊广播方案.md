# 群聊广播方案

## 1. 目标

基于现有的集群路由架构，实现**读扩散**模型的群聊消息广播功能。要求：

- 一条群消息只需 **1 次 DB 写入**
- 消息投递链路尽可能少 Redis/DB 查询
- 各节点只查自己的 `DashMap`，不跨节点
- 支持在线成员 QUIC 推送 + 离线成员上线后拉取

---

## 2. 核心原则

### 2.1 群聊用广播，单聊用 hash 路由

```
群聊 → 1 条消息 → N 个接收者 → 所有节点都有活干 → 广播
单聊 → 1 条消息 → 1 个接收者 → 其他节点白干活 → hash 精确路由
```

互不干扰，各用各的最优方案。

### 2.2 一次查成员列表，多处复用

接收节点从 Redis/DB 查询一次全量群成员列表后，**随广播消息一起下发**，其他节点不再重复查询：

```
接收节点 → 查成员列表（1 次 Redis）
        → 将消息 + 成员列表打包广播到所有内网节点
             → 各节点直接用成员列表 + 本机 DashMap，0 次 Redis
```

---

## 3. 消息流程

### 3.1 完整时序

```
发送者 A                   Node 1 (接收节点)         Node 0 / Node 2     Redis / DB
    │                             │                       │                  │
    │── 群消息 ──────────────────►│                       │                  │
    │                             │                       │                  │
    │                             │── 查群成员列表 ──────────────────────────►│
    │                             │◄── ["A","B","C","D"] ────────────────── │
    │                             │                       │                  │
    │                             │── 校验 A 是否在群内 ── │                  │
    │                             │   通过 ✓              │                  │
    │                             │                       │                  │
    │                             │── 广播到 Node 0 ─────►│                  │
    │                             │   {msg, ["A","B.."]}  │                  │
    │                             │                       │── 查本机 DashMap │
    │                             │                       │   B→在线→投递 ✓  │
    │                             │                       │   (A,C,D 不在)   │
    │                             │                       │                  │
    │                             │── 广播到 Node 2 ─────►│                  │
    │                             │   {msg, ["A","B.."]}  │                  │
    │                             │                       │── 查本机 DashMap │
    │                             │                       │   D→离线→跳过    │
    │                             │                       │   (A,B,C 不在)   │
    │                             │                       │                  │
    │                             │── 本机处理             │                  │
    │                             │   查本机 DashMap       │                  │
    │                             │   A(自己)→跳过         │                  │
    │                             │   C→在线→投递 ✓       │                  │
    │                             │                       │                  │
    │                             │── 持久化群消息 ────────────────────────► │
    │◄── ACK ─────────────────── │                       │                  │
```

### 3.2 关键说明

| 步骤 | 说明 |
|------|------|
| **查成员列表** | 由接收节点执行，缓存命中走 Redis，未命中走 DB |
| **校验** | 确认发送者 A 是群成员，否则直接拒绝 |
| **广播** | 通过内网 QUIC 发送到除自己外的所有节点 |
| **本机处理** | 不走网络；实际为 `process_group_broadcast_local()` 与 `process_group_broadcast()` 两个独立函数（逻辑相同，均带去重），并非共用同一函数 |
| **持久化** | 由接收节点写入 DB，**只需 1 条**（实际在构造广播**之前**以 `tokio::spawn` 异步执行） |

## 5. 核心代码逻辑

### 5.1 接收节点处理入口

```
quic_service/src/msg_service/group_msg_service.rs
```

```rust
/// 实际签名：crates/quic_service/src/msg_service/group_msg_service.rs
pub async fn handle_group_msg_from_client(
    core: &CoreState,
    group_msg: GroupQuicMsg,
    server_index: u32,
    connections: &ConnectionsMap,
) -> anyhow::Result<()> {
    // 1. 序列化群消息体（粘包协议格式）
    let msg_bytes = serialize_group_msg(&group_msg)?;

    // 2. 从 Redis/DB 查全量群成员列表（1 次查询）
    //    实际：get_group_members_cached(core, &group_msg.group_uuid)
    let all_members = get_group_members_cached(core, &group_msg.group_uuid).await?;

    // 3. 校验发送者是否在群内
    if !all_members.contains(&group_msg.send_user) {
        return Err(anyhow!("发送者不在群成员列表中"));
    }

    // 4. 持久化消息（实际在构造广播之前，以 tokio::spawn 异步执行）
    //    save_group_message_to_db(rb: &RBatis, group_msg: &GroupQuicMsg)
    //    —— 签名是 (rb, group_msg)，不接收 nano_id 单独参数

    // 5. 构造广播消息，带上成员列表
    let broadcast = InternalGroupBroadcast {
        broadcast_type: match group_msg.msg_type {
            2001 => BroadcastType::GroupText,
            2002 => BroadcastType::GroupImage,
            2003 => BroadcastType::GroupFile,
            _ => BroadcastType::GroupNotification,
        },
        group_uuid: group_msg.group_uuid,
        msg_bytes,
        sender: group_msg.send_user,
        all_members,
        source_node: server_index,
        timestamp: group_msg.timestamp,
        broadcast_id: group_msg.nano_id,
    };

    // 6. 获取所有内网节点地址，向其他节点广播
    let nodes = get_all_internal_node_addresses().await?;
    for (node_index, addr) in &nodes {
        if *node_index == server_index {
            continue;
        }
        // 即使某个节点失败也不影响整体
        let _ = send_internal_group_broadcast(*addr, &broadcast).await;
    }

    // 7. 本机处理（不走网络，直接调用本地逻辑）
    process_group_broadcast_local(&broadcast, connections).await?;

    Ok(())
}
```

### 5.2 各节点收到广播后的处理

```
quic_service/src/msg_service/group_msg_service.rs (同文件)
```

```rust
/// 各节点收到内网 QUIC 广播后的处理
/// 用广播中携带的成员列表 + 本机 DashMap 投递，不查任何外部存储
pub async fn process_group_broadcast(
    broadcast: &InternalGroupBroadcast,
    connections: &ConnectionsMap,
) -> anyhow::Result<()> {
    for member in &broadcast.all_members {
        // 跳过发送者自己
        if *member == broadcast.sender {
            continue;
        }

        // 直接查本地 DashMap——在就在，不在就跳过
        let conn = find_online_connection(member, connections);
        if let Some(conn) = conn {
            let mut send = conn.open_uni().await?;
            send.write_all(&broadcast.msg_bytes).await?;
            send.finish().await?;
        }
    }

    Ok(())
}

/// 查本机 DashMap 找用户的在线连接
fn find_online_connection(
    user_uuid: &str,
    connections: &ConnectionsMap,
) -> Option<quinn::Connection> {
    for platform in [PC_PLATFORM, MOBILE_PLATFORM] {
        let key = format!("{}:{}{}{}{}",
            platform,
            REDIS_QUIC_SERVERS,
            user_uuid,
            REDIS_SPLIT,
            ConnectionType::Text,
        ).to_uppercase();

        if let Some(entry) = connections.get(&key) {
            return Some(entry.conn.clone());
        }
    }
    None
}
```

```rust
/// 内网 QUIC 路由入口（设计稿，未接线）
/// 根据消息类型分发到不同的处理路径
pub async fn route_internal_request(
    core: &CoreState,          // 实际签名含 core
    request: &[u8],
    connections: &ConnectionsMap,
    server_index: u32,
) -> Result<Vec<u8>> {
    // 尝试反序列化为群聊广播
    if let Ok(broadcast) = bincode::deserialize::<InternalGroupBroadcast>(request) {
        process_group_broadcast(&broadcast, connections).await?;
        return Ok(bincode::serialize(&InternalGroupBroadcastResponse::ok())?);
    }

    // 尝试反序列化为单聊路由请求
    if let Ok(msg) = bincode::deserialize::<InternalQuicRequest>(request) {
        let resp = route_request(&msg, connections, server_index).await?;
        return Ok(bincode::serialize(&resp)?);
    }

    Err(anyhow!("未知的内网 QUIC 请求类型"))
}
```

## 7. 去重处理

### 7.1 为什么需要去重

在某些异常场景下可能出现重复广播：

- 节点收到广播后回传
- 网络抖动导致重试
- 节点刚恢复，收到历史广播

### 7.2 实现方案

```rust
use dashmap::DashSet;
use std::sync::Arc;

pub struct BroadcastDedup {
    set: Arc<DashSet<String>>,
}

impl BroadcastDedup {
    pub fn new() -> Self {
        let set = Arc::new(DashSet::new());

        // 每 60 秒清空一次（广播 ID 只短时间有效）
        let cloned = set.clone();
        tokio::spawn(async move {
            loop {
                tokio::time::sleep(Duration::from_secs(60)).await;
                cloned.clear();
            }
        });

        Self { set }
    }

    /// true = 首次见到（可以处理）
    /// false = 已处理过（跳过）
    pub fn try_process(&self, broadcast_id: &str) -> bool {
        self.set.insert(broadcast_id.to_string())
    }
}
```

### 7.3 集成到广播处理

```rust

static DEDUP: Lazy<BroadcastDedup> = Lazy::new(BroadcastDedup::new);

    connections: &ConnectionsMap,

        return Ok(()); // 已处理过，跳过

}
```

### 8.2 用户上线时同步

```rust
/// 用户上线后，拉取所有群的未读消息
/// ⚠️ 实际签名：(core: &CoreState, user_uuid: &str, connections: &ConnectionsMap)，
///    且全仓库无调用者——external/quic_server.rs::user_online() 是 TODO 空壳，
///    上线并不触发同步。函数已实现但未接入上线流程。
pub async fn sync_offline_group_messages(
    core: &CoreState,
    user_uuid: &str,
    connections: &ConnectionsMap,
) -> anyhow::Result<()> {
    let groups = get_user_groups(user_uuid).await?;

    for group in groups {
        let unread = GroupMessageRecord::select_unread(
            &group.group_uuid,
            group.last_read_msg_id,
        ).await?;

        for msg in unread {
            let msg_bytes = serialize_group_msg_as_bytes(&msg)?;
            if let Some(conn) = find_online_connection(user_uuid, connections) {
                let mut send = conn.open_uni().await?;
                send.write_all(&msg_bytes).await?;
                send.finish().await?;
            }
        }
    }

    Ok(())
}
```

## 11. Redis 缓存策略

### 11.1 群成员列表缓存

**实际实现**（与设计稿有出入）：

- key 实际为 `GROUP:MEMBERS:{group_uuid}`（大写，uuid 转大写），不是小写 `group:members:`
- quic_service 的 `get_group_members_cached` 用无 TTL 的 `set` 写入（近似永不过期）✓
- 但 http_service 的 `sync_group_members_to_redis`（`group_service.rs`）用 `set_ex(..., 1800)` 写 30 分钟 TTL —— 两处写入方策略不一致

| 方式 | 评估 |
|------|------|
| TTL = -1 + 手动失效 | 实时一致，成员退群后立即不被推送（quic_service 读取侧） |
| TTL = 1800s | http_service 写入侧实际策略，最多 30 分钟脏窗口 |

| **群成员列表** | Redis 缓存，quic 读取侧无 TTL / http 写入侧 1800s | ⚠️ 手动失效未实现（见 §11.2），依赖 TTL 过期 |
| **成员列表获取** | 接收节点查 1 次 | 随广播下发，其他节点不复查 |
| **在线判定** | 各节点查本地 DashMap | 0 次网络开销，0 次 Redis |
| **节点间通信** | 内网 QUIC 广播 | 1 条消息达到所有节点（接收节点 SCAN `INTERNAL:QUIC:SERVER:*` 获取地址，带 5s NODE_CACHE） |
| **消息持久化** | 接收节点写 DB | 1 条记录（广播前异步执行） |
| **去重** | broadcast_id + DashSet | 防网络抖动/重试导致的重复广播；每 60s 清空 |
| **离线同步** | last_read_msg_id + 上线拉取 | ⚠️ 函数已实现但未接入上线流程（`user_online()` 为 TODO 空壳） |
| **扩缩容** | 无影响 | 新节点启动后自动回源 DB |
| **单聊路由** | hash % N 单跳直达 | 无 Redis 兜底；内网两阶段路由（§6）未接线 |
